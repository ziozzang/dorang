## 0. 범위

### 0.1 dorang이란

Go로 작성된 단일 바이너리 LLM 게이트웨이. 호출자를 인증하고, 요청을 여러 대체 가능한
백엔드 중 하나로 라우팅하며, **실제 프로바이더 플랜의 구조와 일치하는** 용량·지출 제한을
집행하고, 무슨 일이 있었는지 기록한다 — **그 기록이 "빠르게 하려고 끄는 것"이 되지 않게.**

### 0.2 확장 범위: 노트북에서 엔터프라이즈까지

같은 바이너리와 같은 설정 파일이 전 구간에서 동작해야 한다. 배포 모델을 바꾸는 게 아니라
**설정을 바꿔서** 확장한다.

| | **노트북** | **팀** | **엔터프라이즈** |
|---|---|---|---|
| 저장소 | SQLite 내장 | PostgreSQL | PostgreSQL, 파티션 |
| 조정 | 없음 | 없음 | Redis 또는 PostgreSQL 리스 |
| 노드 | 1 | 1–2 | N, 리더 선출 유지보수 |
| 용량 정확성 | 정확 | 정확 | 정확(공유) 또는 상한 있는 초과(리스) |
| 계측 | 인프로세스, 샘플링 | 전체 원장 | 원장 + 롤업 + 보존정책 |
| 필수 의존성 | **0** | 1 | 2 |
| 목표 처리량 | 수백 req/s | 수천 req/s | 노드당 10k+ req/s |

설계 전반이 지켜야 할 두 귀결:

- **노트북에서 못 돌리는 것은 무엇도 필수가 될 수 없다.** Redis, 메트릭 스택, 별도 DB는
  전부 선택이다. 설정 파일 하나와 `dorang` 프로세스 하나로 요청을 처리할 수 있어야 한다.
- **구조적으로 단일 노드인 것은 없다.** 상태를 갖는 모든 메커니즘은 N 노드에서의 동작을
  선언한다. "N > 1이면 기동 거부"도 명시적 답변으로 인정한다.

### 0.3 full protocol, 그리고 동반 조건으로서의 속도

추론 프로토콜은 스트리밍 포함 **전량** 구현한다. 프로바이더 고유 경로는 어댑터를 하나씩
쓰는 대신 **범용 패스스루 엔진 하나**(§10.6)로 덮는다. 관리·엔터프라이즈 표면은 단계적으로
채우고, 미구현 경로는 조용한 `404`가 아니라 **사유가 담긴 `501`** 로 답한다.

속도는 여기에 붙는 제약이 아니라 **동반 조건**이다. 프로토콜을 추가해도 핫패스 비용이
늘어선 안 된다. §10.1이 중립 표현(N×M이 아닌 N+M)을 쓰는 이유, §10.6이 존재하는 이유,
§15가 협상 불가인 이유가 정확히 이것이다.

## 1. 아키텍처

```
L1 Frontend  프로토콜 어댑터 (openai-chat / responses / anthropic-messages / …)
      ↓ CanonicalRequest
L2 Gate      인증 · 쿼터 · 어드미션
      ↓
L3 Router    alias → 그룹 → 배포 / sticky · prefix · cost · latency / 폴백 · 서킷브레이커
      ↓
L4 Capacity  다축 예약
      ↓
L5 Backend   프로바이더 어댑터
      ↓
L6 Meter     비동기 회계 + 트레이스
```

단일 프로세스. 워커 프로세스 분할 없음 — Go 런타임이 코어를 쓴다. Redis는 선택이며,
노드 간 **정확한** 공유 용량이 필요할 때만(§5.6) 필수가 된다.

## 2. 상호운용성

dorang은 특정 제품의 포크나 재작성이 아니다. 두 층위에서 상호운용하며, 둘 다
**테스트가 있는 기능**으로 다룬다.

### 2.1 와이어 상호운용 — 엄격

클라이언트 SDK가 수정 없이 동작해야 한다. 골든 테스트로 고정한다.
`/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/rerank`, `/v2/rerank`,
`/v1/messages`(+`count_tokens`), `/v1/responses`, `/v1/audio/*`, `/v1/images/*`,
`/v1/moderations`, `/v1/ocr`, `/v1/models`, `/v1/files`, `/v1/batches`, `/health/*`,
`/metrics`. 인증은 `Authorization: Bearer`, `x-api-key`, `api-key`를 모두 받는다.

구체적 와이어 계약은 [COMPATIBILITY.ko.md](COMPATIBILITY.ko.md)에 있다.

#### 모델 이름은 불투명하다 — 규칙 하나, 예외 없음 **[R1-C3]**

실제 모델 이름은 `:`를 최소 세 가지 용도로 쓴다: 패밀리 태그(`family:31b`),
벤더 프리픽스(`vendor:model-5.1`), 배포 변종(`model-flash:cloud`). 어떤 코드 경로는 `:`로
쪼개고 어떤 경로는 보존하면, **같은 모델에 대해** 식별·라우팅·alias·prefix 어피니티가
전부 비결정적이 된다.

개정 1은 이 규칙을 적어놓고 스스로 어겼다 — 프로바이더 프리픽스 추론, import 시
`provider/model` 분해, prefix 해시에 들어가는 미정의 그룹 id 정규화. 개정 2는 규칙 하나로 고정한다.

1. **모델 이름은 불투명 문자열이다.** 어떤 컴포넌트도 어떤 문자로도 쪼개지 않는다.
2. **프로바이더 식별은 명시적 설정 필드에서만** 온다 — `providers[].name`,
   `deployments[].upstream_model`. 모델 문자열 파싱에서 오지 않는다.
3. **프리픽스 기반 능력 추론**(§4.3)은 *설정된* upstream model을 읽어 **기본값만** 고른다.
   식별·라우팅·해싱에는 영향이 없다.
4. `model_group_id`의 정규화 함수는 **하나**다. prefix 해시 시드(§7.4b)를 포함한 모든
   호출자가 같은 함수를 쓴다.
5. import는 `provider/model` 필드를 **선언된 프로바이더 목록과 대조해** 매핑하며,
   구분자로 쪼개지 않는다. 해석 불가한 것은 추측하지 않고 보고한다.

콜론이 들어간 실제 이름들을 골든 테스트로 박제해, 이 부분의 회귀는 크게 실패하도록 한다.

### 2.2 설정 상호운용 — import

널리 쓰이는 프록시 형식의 선언적 모델 목록 설정을 읽어(`dorang import config <file>`)
dorang 스키마로 정규화하고, 표현할 수 없었던 것을 보고한다.

| 원본 개념 | dorang |
|---|---|
| `model_list[].model_name` | `models[].name` — 중복 선언이 로드밸런싱 그룹을 만든다 |
| `model_list[].<params>.model` | `deployments[].upstream_model` |
| `.api_base` / `.api_key` / 프로바이더 힌트 | `providers[]` + `credentials[]`로 정규화 |
| `.rpm` / `.tpm` / `.max_parallel_requests` | 배포의 `limits[]` |
| drop-unsupported / 명시 drop 목록 | `params.drop_unsupported`, `params.drop[]` |
| 토큰당 입출력 단가 | `pricing.rules[]` (§8) |
| 라우팅 전략 | `models[].strategy` |
| default / context-window / content-policy 폴백 | `fallbacks.on.*` (§7.6) |

### 2.3 관리 상호운용 — 형태 호환

기존 스크립트·UI가 계속 동작하도록 흔한 관리 경로의 형태를 유지한다:
`/key/*`, `/user/*`, `/team/*`, `/model/*`, `/model_group/info`, `/budget/*`,
`/spend/{logs,calculate}`, `/global/spend/report`, `/{user,team,tag}/daily/activity`,
`/health/history`. 그 외는 기계가 읽을 수 있는 사유와 함께 `501`.

### 2.4 크리덴셜 import **[R1-A]**

기존 크리덴셜 import는 **이관 창구**이지 아키텍처가 아니다.

- dorang이 발급하는 키는 `dorang_v1`: `HMAC-SHA256(pepper, token)`.
  DB가 유출돼도 오프라인 공격이 성립하지 않는다.
- `legacy_sha256`(솔트 없는 단일 라운드 다이제스트)은 `auth.legacy.enabled: true`일 때만
  지원하며, **`auth.legacy.until: <날짜>` 를 필수로 요구**한다. 그 날짜 이후 거부한다.
- importer는 **만료와 폐기를 반드시 존중**한다. 실제 배포를 검증한 결과 저장된 크리덴셜의
  대다수가 이미 만료 상태였다. 이를 살아있는 것으로 가져오면 **폐기된 접근 권한을 조용히
  되살리는** 것이 된다. 만료된 행은 만료된 채로 들어온다.
- 다음 권한 필드를 가져오지 않으면 게이트웨이가 **fail-open** 한다: 만료, 차단 플래그,
  모델 허용목록, 라우트 허용목록, 예산/지출/리셋시각, 레이트 한도, 소속 팀·유저,
  오브젝트 권한 참조.
- 관리자/마스터 크리덴셜은 **out-of-band** 이다 — 설정값과 상수시간 비교하며 행으로
  저장하지 않는다. DB만 읽는 게이트웨이는 관리자 인증을 통째로 잃는다.
- 비밀의 뒷자리를 담는 표시용 컬럼은 **그대로 복사하지 않는다.** dorang은 되돌릴 수 없는
  표시 라벨을 저장한다.
- 봉인된 저장소에서 프로바이더 크리덴셜도 가져온다면, **봉인 키를 회전하기 전에** 읽어야
  한다. 봉인 키가 관리자 키로 폴백하는 구성에서는 회전이 저장된 프로바이더 크리덴셜을
  전부 파괴한다.

**두 스킴이 공존해도 조회는 한 번이다.** 스킴 무관 인덱스 키
`lookup = sha256(token)[:16]` 로 행을 고르고, 검증만 스킴별로 분기한다.
`auth.rehash_on_use`가 켜져 있으면 레거시 검증 성공 시 `dorang_v1`으로의 비동기 업그레이드를
예약하므로, 무중단·무플래그데이로 이관이 끝난다.

## 4. 설정

### 4.1 원칙

- **파일이 기준선, DB가 위에 덮인다.** 파일만으로 완전히 기동 가능해야 한다.
- **비밀은 설정에 들어가지 않는다.** `key_env`, `key_file`, `key_ref`.
  인라인 리터럴은 `server.env: development`에서만 허용, 아니면 기동 거부.
- **모든 섹션이 hot-reload.** 파일 watch, `SIGHUP`, 관리 엔드포인트.
  진행 중 요청은 시작할 때의 스냅샷을 계속 쓴다(§15.2).

### 4.2 형태

영문 [DESIGN.md §4.2](DESIGN.md#42-shape)의 YAML을 그대로 사용한다. 핵심만 발췌:

```yaml
storage: { driver: sqlite }          # sqlite | postgres
cluster: { enabled: false, capacity_mode: local }

capacity:
  provider_groups:  { cloud-a-pool: { max_concurrency: 6 } }
  credential_groups:
    acct-1: { max_concurrency: 3 }   # ← 계정당, 모델 무관
    acct-2: { max_concurrency: 3 }
  models:
    - { provider: plan-a, model: model-x, max_concurrency: 7 }   # ← (키, 모델)당
    - { provider: plan-a, model: model-y, max_concurrency: 7 }
  interactive_reserve: 0.3           # §11.1 — batch가 침범 못 하는 몫

routing:
  prefix:
    chunk_bytes: 4096                # 바이트 경계 — 핫패스에 토크나이저 없음 [R1-4]
    checkpoints: logarithmic         # [R1-5]
    max_bytes: 64MiB                 # 엔트리 수가 아니라 메모리로 예산 [R1-6]

metering:
  numeric: { enabled: true }                                    # 항상 유지 [R1-2]
  trace:   { store_messages: truncated, truncate_chars: 512,
             sample_rate: 1.0, daily_byte_budget: 8GiB }        # [R1-3]
  spool:   { dir: ~/.dorang/spool, max_bytes: 2GiB }            # [R1-1]
```

### 4.3 프로바이더 kind

`kind` 한 단어가 와이어 어댑터·능력 기본값·프롬프트 캐시 스킴·리즈닝 제어 형태를 한꺼번에
고른다. 세 층이 뒤가 앞을 덮으며 합성된다:
**kind 기본값 → 모델명 프리픽스 규칙 → 명시 설정.**

`openai`, `openai-responses`, `anthropic`, `glm`, `qwen`, `deepseek`, `moonshot`,
`minimax`, `mistral`, `xai`, `google`, `ollama`, `openrouter`, `cohere`, `jina`,
`vllm`, `bedrock`, `vertex`, `azure`, `echo`.

## 5. 용량 — 다축 예약

가장 어려운 요구사항. **한 프로바이더 안에서도 동시성 한도가 세는 단위가 다르다.**
어떤 계정은 모든 모델을 합쳐 3개, 어떤 코딩 플랜은 *모델별* 7개 — 모델 두 개면 한 키에서
동시 14개가 된다.

### 5.1 축

| 축 | 키 | 설정 위치 | 예 |
|---|---|---|---|
| `route` | `route:<provider>` | `providers[].max_concurrency` | 배포 자체의 천장 |
| `provider_group` | `pgroup:<g>` | `capacity.provider_groups` | 여러 프로바이더가 공유하는 풀 |
| `model` | `model:<provider>\0<model>` | `capacity.models[]` | **(키, 모델)당** |
| `credential_group` | `cgroup:<g>` | `capacity.credential_groups` | **계정당, 모델 무관** |
| `key` | `key:<provider>\0<cred>` | `key_rotation…keys[]` | 키 자체의 천장 |
| `principal` | `prin:<key\|user\|team>` | `capacity.principals` | 호출자별 |
| `global` | `global:` | `capacity.global` | 프로세스/클러스터 천장 |

### 5.2 지표

`max_concurrent`(게이지, 예약 후 완료 시 반환) · `rpm`(레이트, 토큰 버킷) ·
`tpm`(레이트, **논리적 요청 단위 정산** §5.5) · `max_queue`(초과 시 `429`).

### 5.3 획득 — 원자적, 전량 또는 전무

```
Acquire(...):
  단일 임계구역에서:
    route → provider_group → model → principal → global 검사
      하나라도 불가 ⇒ 아무것도 잡지 않은 채 전체 실패
    크리덴셜 후보를 (선호 우선) 순회하며 그 후보의 (credential_group, key) 검사
      on_capacity=wait  ⇒ 선호 후보만 시도
      on_capacity=spill ⇒ 다음 후보로
    커밋: 선택된 키 전부를 한 번에 증가
  실패 ⇒ 막은 축의 큐에 등록하고 대기 (§5.4)
```

검사와 커밋이 하나의 임계구역이므로 **부분 점유가 존재하지 않고**, 한 슬롯을 잡은 채
다른 슬롯을 기다리는 상태도 없다. 데드락은 구조적으로 불가능하다.

**프로바이더를 넘는 후보 원자성 [R1-11].** 모델 그룹은 여러 프로바이더에 걸칠 수 있어
`spill`이 *다른* 프로바이더의 크리덴셜 축으로 이동할 수 있다. 규칙: 크리덴셜 후보는
`(provider, credential_group, key)` 트리플이며 **한 단위로** 검사·커밋된다. spill은 트리플
전체를 교체한다. 프로바이더 종속 축은 앞 후보 것을 물려받지 않고 새 후보 기준으로 재도출한다.

**예약 만료.** `defer Release()` 외에 모든 예약이
`deadline = now + request_timeout + 30s`를 갖고, 스위퍼가 만료된 예약을 회수한다.

**클라이언트 단절이 업스트림으로 전파된다 [R1-10].** 스트리밍 클라이언트가 사라졌을 때
로컬 슬롯만 반환하는 것으로는 부족하다 — 업스트림은 여전히 그 요청을 자기 한도에 세고
있으므로, dorang은 곧바로 꽉 찬 업스트림에 다음 요청을 보내 `429`를 받는다. 따라서 취소를
전파해 **업스트림 연결을 먼저 중단**한 뒤 슬롯을 반환한다. 로컬 in-flight와 업스트림
in-flight가 발산해서는 안 된다.

### 5.4 대기 — 축별 FIFO, 표적 깨우기 **[R1-7]**

개정 1은 해제 때 모든 대기자를 깨웠다. 작은 한도 뒤에 많은 요청이 줄 서 있으면 하나만
성공하고 나머지는 락을 다시 잡아 재검사하고 다시 잠든다 — 실패한 락 획득이 유용한 작업을
압도하고 도착 순서도 사라진다. 더 나쁜 것은, 여러 축이 필요한 대기자가 한 축만 필요한
대기자에게 체계적으로 지므로 **일반적인 경우가 기아 상태**가 되어 결국 `429`가 된다.
호출자 입장에서 이것은 데드락과 구별되지 않는다.

개정 2:

- 각 축이 **FIFO 대기열**을 갖는다.
- 대기자는 자신을 막은 축에 등록하며, 필요한 전체 축 집합을 기록한다.
- 해제 시 그 축은 **비워진 슬롯 수만큼만** 큐 선두를 깨우고, 재경쟁 신호가 아니라
  **직접 부여**한다.
- 그사이 다른 축이 차버린 대기자는 **원래 등록 시각을 지닌 채** 새로 막힌 축의 선두로 간다.
- **에이징**: 총 대기 시간에 비례해 유효 우선순위가 오르므로, 다축 대기자가 단축 대기자에게
  무한히 추월당하지 않는다.

완료 게이트: 대기자 0/100/1000 × 한도 1/7/32 포화 벤치마크. 해제당 깨우기 수가 상한 이내,
축 내 FIFO 공평성, 다축 대기자 무기아를 단언한다.

### 5.5 TPM은 논리적 요청에 귀속된다 **[R1-8]**

개정 1은 자기모순이었다. 한 절은 TPM을 실측으로 정산한다 했고, 다른 절은 레이트는 롤백이
필요 없다 했다. 둘 다 참일 수 없고, 폴백과 결합하면 두 번째가 해롭다 — 세 홉이 각각
선차감하면 논리적 요청 하나가 TPM을 세 배 쓴다.

- 입력 토큰은 전송 전 정확히 센다. 출력은 `max_tokens`로, 없으면 모델 최대 출력의 정해진
  비율로 선차감한다.
- **모든 선차감에 논리적 요청 id를 태그한다.** 완료 시 성공한 홉만 실측으로 정산하고,
  **실패한 홉은 전액 환불**한다.
- RPM은 환불하지 않는다 — 업스트림에 도달한 요청은 실패했더라도 요청 슬롯을 소비했다.
  이 비대칭은 의도된 것이며 명시한다.

### 5.6 다중 노드 **[R1-1, R1-3]**

| `capacity_mode` | 동작 | 정확성 |
|---|---|---|
| `local` | 노드별 카운터 | **1노드에서 정확, N노드에서 N배 초과** |
| `shared-redis` | Lua 원자 획득/해제 + 리스 TTL | 정확, 핫패스 +1 RTT |
| `shared-pg` | 리스 테이블 + advisory lock | 정확, +1 RTT (더 큼) |
| `leased` | 노드가 블록을 리스받아 로컬 차감, 리더가 재분배 | **초과 ≤ 블록크기 × (노드−1)** |

**하드 가드.** `cluster.enabled: true` + `capacity_mode: local` 조합은 **기동을 거부한다.**
개정 1은 이것을 권고로 뒀다. 권고가 아니다: 프로바이더 플랜 한도를 조용히 넘기면 업스트림
`429`가 나오고, 그것이 폴백 체인(§7.6)으로 번져 **같은 클래스의 무관한 모델 용량까지**
갉아먹는다. 장애가 원인에서 멀리 떨어진 곳에 나타난다.

작은 한도(한 자릿수)는 노드로 쪼갤 수 없으므로 `leased`는 `cluster.min_leasable`(기본 16)
미만 한도를 거부하고 공유 모드를 요구한다.

모든 모드가 **최대 초과량을 수치로** 공표한다. "대략 정확"은 명세가 아니다.

### 5.7 구현과 그 진화 **[R1-2]**

v1은 브로커 전체를 단일 뮤텍스로 감싼다: 단순하고, 명백히 옳고, 임계구역이 짧다.
그대로 출시하고 **측정**한다.

측정이 샤딩을 요구하면, 샤드 키는 **프로바이더**이며 **한 예약의 모든 축 키가 하나의 샤드로
귀결된다는 것이 하드 불변조건**이다. 이는 구성으로 강제된다: `route`, `provider_group`,
`model`, `credential_group`, `key`가 전부 프로바이더 종속이고, `spill`이 후보 트리플 전체를
교체하므로(§5.3) 예약이 프로바이더를 가로지르지 않는다.

프로바이더에 종속되지 않는 두 축은 샤드 **바깥, 그 앞에서** 단순 원자 카운터로 처리한다.
`global`과 `principal`은 단일 카운터라 CAS가 즉시 성공하거나 실패하며, 대기 중 홀딩이 없다.
순서는 global → principal → 프로바이더 샤드로 고정이므로 사이클이 없다.

개정 1은 샤드를 넘는 예약의 원자성을 말하지 않은 채 샤딩을 제안했고, 그대로 갔다면
데드락 또는 부분 점유를 다시 불러왔을 것이다. 위 불변조건이 이 진화를 안전하게 만들며,
주석이 아니라 **테스트로** 단언한다.

## 6. 쿼터와 예산

§5와 직교한다. 동시성은 "지금 몇 개", 쿼터는 "기간 내 얼마".

### 6.1 로컬 계측 쿼터

```yaml
quotas:
  - { window: 5h,     metric: cost_usd,     limit: 3.0, on_exhaust: cooldown }
  - { window: weekly, metric: tokens_total, limit: 200000000 }
```

윈도우는 분 단위 버킷 링으로 O(1)이다. `on_exhaust`는 `cooldown`(리셋까지 물러남 —
R4의 "다른 키로 전환"이 여기서 일어난다), `disable`, `passthrough`.

### 6.2 프로바이더 보고 쿼터 — 대체가 아니라 합성 **[R1-4]**

프로바이더가 잔량을 노출하면 그 값은 dorang을 거치지 않은 사용까지 **전부** 포함하므로
로컬 계측만으로는 과소 집계된다. 그러나 폴링은 최대 한 주기만큼 낡았고, 버스트 중에는
로컬 카운터가 **더 최신** 신호다. 개정 1은 프로바이더를 "진실"로 선언하고 로컬 델타를
버렸는데, 그러면 **정보가 가장 나쁜 순간에 가장 공격적으로** 라우팅하게 된다.

```
effective_used = max( 프로바이더_보고값 ,
                      마지막_폴_시점_보고값 + 그_이후_로컬_델타 )
```

폴링마다 프로바이더 값이 기준선을 재설정하고, 그 사이는 로컬 계측이 델타를 공급한다.
어느 쪽도 버스트를 숨길 수 없다.

폴링은 요청 경로 밖에서 병렬로, 프로바이더별 타임아웃과 함께 돈다. **폴링 실패는 절대
크리덴셜을 비활성화하지 않는다** — 읽기 실패는 소진이 아니다. 마지막 성공 스냅샷을 유지하고
낡은 정도를 노출한다.

### 6.3 노드 간 쿼터 **[R1-2]**

개정 1은 원자적 공유 쿼터, 비동기 로컬 계수, 핫패스 무동기접근을 동시에 약속했다.
셋 다 참일 수 없다 — 수렴 전에 노드들이 초과하거나, 매 요청이 한 행을 경합한다.

개정 2는 §5.6의 모드 체계를 쿼터에도 그대로 적용한다(`local`/`shared-redis`/`shared-pg`/
`leased`). 같은 하드 가드, 같은 "최대 초과량 수치 공표" 요구. 쿼터와 동시성이 두 개가 아니라
하나의 정확성 어휘를 쓰게 된다.

### 6.4 예산

예산은 **쓰기 전에 선점**하므로 동시 요청이 상한을 넘지 못한다. 추정치는 의도적으로
상한이다(입력 토큰 정확 + 출력은 `max_tokens` 기준).

검토에서 나온 두 가지 수정:

- **예약이 만료된다 [R1-5].** 선점과 정산 사이에 프로세스가 죽으면 그 금액이 영원히 잠기고,
  시간이 지나면 **아무도 쓰지 않은 돈**으로 예산이 소진된다. 리더가 만료된 홀드를 회수하며,
  이는 §5.3의 용량 예약과 정확히 같은 패턴이다. 두 메커니즘이 같은 안전망을 갖는다.

  > **만료가 어디에 있고 어디에 없는가.** 이 항목은 원래 "`budget_state`가 `reserved_until`을
  > 갖는다"였고, 그에 맞춰 두 개의 컬럼과 네 개의 스토어 메서드(`ReserveBudget`,
  > `SettleBudget`, `ReleaseReservation`, `SweepExpiredReservations`), 그리고 매 틱마다
  > 그것을 쓸어내는 리더 잡이 있었다. 어느 것도 실행된 적이 없다. `ReserveBudget`은 자기
  > 테스트 밖에 호출자가 없었으므로 모든 배포의 모든 행에서 `reserved_nano`는 0이었고,
  > 스윕의 `WHERE reserved_nano > 0`은 성립할 수 없는 술어에 대한 틱당 스토어 왕복이었다.
  >
  > 실제로 존재하는 홀드는 §9.6의 **리스 블록**이다. 노드가 블록을 뽑고, 한 단위를 내주기
  > 전에 블록 전체가 `spent_nano`에 기록되며, 단위 자체는 원자적 연산 뒤 메모리에 있다.
  > 만료는 `quota_leases`의 `expires_at`이고, 리더의 리스 회수 패스가 TTL이 지난 모든
  > 리스에 대해 `amount - used`를 되돌린다. 이 안전망은 대체된 것보다 엄격히 넓다:
  > **이미 기록된 블록을 쥔 채 죽은 노드**까지 덮으며, 그것이 죽은 프로세스가 실제로 남기는
  > 상태이고 예약 스윕이 결코 회수할 수 없던 것이다.
  >
  > 둘을 함께 유지할 수는 없었고, 단정함의 문제가 아니다: 블록을 `spent_nano`에 기록하면서
  > `reserved_nano`에도 선점하면 같은 돈을 두 번 센다. `Ledger.readCounter`가 두 컬럼을
  > 더하고 있던 이유가 그것이다. 예약 코드와 그 컬럼(마이그레이션 `0006`), 스윕 잡,
  > 그리고 이 항목의 이전 본문은 모두 삭제되었다.
- **실행되지 않은 요청은 전액 환불 [R1-6].** 요청이 게이트에서 예산을 선점한 뒤 용량 대기
  중 거절되어 업스트림에 도달하지 못할 수 있다. 개정 1은 "완료 후 정산"만 정의했다.
  개정 2는 게이트에서는 **soft hold**, **용량 획득 후에 hard hold**로 바꾼다. 전송 전에
  실패하는 모든 경로는 전액을 반환한다.

예산 초과는 폴백 조건이 **아니다** — 실패하는 것이 옳다.

## 7. 라우팅

### 7.1 파이프라인

```
alias 해석 → 그룹 해석 → 필터(health, quota, budget, policy, capability)
  → 전략 정렬 → 획득 시도(§5.3, 실패 시 다음 후보)
  → 실행 → 오류 분류 → 폴백(§7.6) → 계측(§12)
```

### 7.2 Alias **[R1-C1]**

업스트림은 항상 **실제** 모델 id를 받는다. 응답 본문의 `model`은 **클라이언트가 요청한
이름**을 돌려주므로 클라이언트 측 비교가 계속 동작한다. 실제 모델은 헤더로 노출한다(§10.4).

개정 1은 스트리밍 청크를 "디코드 없이 바이트 오프셋으로 패치"할 수 있다고 했다. 틀렸고,
그것도 예외가 아니라 **일반적인 경우**에 틀렸다.

- **길이가 기본적으로 다르다.** alias는 이름이 다르라고 있는 것이다. in-place 바이트 교체는
  길이가 같아야만 가능한데 그게 예외다.
- **프레임 경계가 임의적이다.** 원시 복사는 버퍼 경계에서 읽으므로 필드가 두 읽기에 걸칠 수
  있다. 첫 버퍼 가정은 필드를 놓치거나 JSON을 손상시킨다.
- **필드가 첫 프레임에 있다는 보장이 없다.**
- **압축**이 걸리면 바이트 패치는 아예 불가능하다.

개정 2의 정직한 메커니즘:

- 스트리밍 응답에 대해 업스트림에 **`Accept-Encoding: identity`** 를 요청한다. 어차피 마지막
  usage 프레임을 읽어야 하므로 압축된 바이트를 원한 적이 없다. 클라이언트 방향 압축은 별개다.
- 릴레이는 JSON 디코더가 아니라 **단일 패스 행 단위 스캐너**다. SSE 프레임 경계로 나누고,
  프레임에 `model`이 있을 때만 값을 다시 쓰며, 부분 프레임을 읽기 간에 이월한다. 나머지는
  손대지 않고 전달한다.
- 비용은 프레임당 할당 없는 메모리 대역폭 수준의 바이트 스캔이다. §15.2는 더 이상
  "zero-copy"를 주장하지 않고 **단일 패스·무디코드**를 주장한다. 그것이 R7을 지키면서
  실제로 달성 가능한 것이다.
- 요청 이름과 업스트림 이름이 같으면 스캐너는 단순 복사로 단락된다.

> 별도 감사에서 독립적으로 확인됐다: 참조 구현은 `model`을 **모든 청크마다** 다시 찍는다.
> 프레임별 재작성은 피해야 할 최적화 대상이 아니라 **요구되는 동작**이다.

### 7.3 전략

`round_robin`(가중) · `least_busy` · `lowest_cost` · `lowest_latency` · `highest_tps` ·
`sticky` · `prefix_sticky` · `priority` · `weighted_random`.
리스트로 주면 tie-break 체인으로 합성된다.

### 7.4 캐시 어피니티

#### (a) 세션 stickiness

키는 `(tenant, group, session)`이며 테넌트가 최상위 성분이라 두 테넌트가 핀을 공유하지
않는다. 엔트리는 마지막 사용이 아니라 **생성** 시각 기준으로 만료된다 — 전제가 "TTL 이후
업스트림 캐시는 사라졌다"이므로, 사용할 때마다 갱신하면 그 전제를 무너뜨린다.

#### (b) prefix 매칭, 순서 정확 **[R1-4, R1-5, R1-6]**

```
c₁, c₂, … = 요청 메시지 바이트를 고정 바이트 경계로 자른 청크
h₀ = H(group_id)
hᵢ = H(hᵢ₋₁ ‖ len(cᵢ) ‖ cᵢ)
```

깊이 *i*에서 일치 ⟹ `c₁..cᵢ`가 **바이트 동일하고 그 순서 그대로**. 순서 교환·삽입·삭제가
모두 다른 값을 만든다. `len`을 섞어 경계 모호성을 제거한다.

- **토큰이 아니라 바이트 경계.** 개정 1은 토큰 경계로 잘랐는데, 그러려면 라우팅 전에 대화
  전체를 토크나이즈해야 한다. 긴 대화에서는 그것만으로 지연 예산 전체를 넘고, 본문 전체
  버퍼링 금지 규칙과도 충돌한다. 체인 성질은 애초에 토큰과 무관했다. 청크는 **원시 요청
  바이트를 스트리밍하며 증분 해시**한다 — 토크나이저도, 두 번째 패스도 없다.
- **로그 간격 체크포인트.** 얕은 고정 깊이는 시스템 프롬프트를 공유하고 이후 갈라지는 두
  대화를 구분할 수 없다 — 가장 깊은 추적 노드에서 충돌하고 "가장 긴 공통 접두사 승리"가
  거짓이 된다. 체크포인트는 초반은 촘촘하고 이후 배가된다: 4 KiB, 8, 16, …, 1 MiB….
- **바이트로 예산.** 개정 1은 낙관적 엔트리 크기로 개수를 셌다. 실제 retained size는 훨씬
  크고, 한 요청이 모든 체크포인트에 엔트리를 쓴다. 테이블은 `max_bytes`로 제한하고, 배포
  id는 정수로 intern하며, retained size 예산은 측정된 마일스톤 게이트다.

### 7.5 우선순위

**dorang 내부**: 어드미션 큐 순서(우선순위 클래스, 클래스 내 FIFO).
**백엔드로**: `vllm`은 body `priority`, OpenAI 계열은 `service_tier`, 그 외는 헤더만.

### 7.6 Fail-back

| 원인 | 기본 체인 |
|---|---|
| `rate_limit` / `quota_exhausted` | same group → same class |
| `context_window` | same class, 더 큰 컨텍스트 |
| `content_policy` | same class |
| `upstream_5xx` | same group → same class |
| `timeout` | same group |
| `budget_exceeded` / `auth` | **없음** |

`same_class`가 R6("동일 클래스 다른 모델로 위임")을 충족한다.

**스트리밍 경계**: 첫 바이트가 클라이언트에 도달하기 **전에만** 폴백한다. 그 후에는 에러
이벤트로 스트림을 끝낸다. 출력 중복은 눈에 보이는 실패보다 나쁘다. 테스트로 강제한다.

## 8. 비용

### 8.1 규칙 클래스 **[R1-9]**

개정 1은 단일 승자 모델이었다. 깨진다: 크리덴셜 범위 구독 규칙이 모델 범위 토큰 규칙을
이겨 토큰 비용을 0으로 만들고, 반대로 합산하면 "가장 구체적인 것이 이김"과 모순된다.
둘은 하나의 비용에 대한 경쟁하는 서술이 아니라 **다른 종류의 비용**이다.

| 클래스 | 의미 | 합성 |
|---|---|---|
| `marginal_usage` | 토큰/요청/문자/초당 | 가장 구체적인 규칙이 이김 |
| `fixed_subscription` | 이 요청과 무관한 플랜 비용 | 가장 구체적인 것이 이김, 기간에 걸쳐 발생 |
| `adjustment` | 할인·마진·세금 | 해당하는 규칙 전부를 순서대로 적용 |

**안분은 공식이 아니라 성질로 규정한다**: *한 기간이 귀속시킨 몫의 합은 플랜 비용과 같고,
그보다 커지지 않는다.* 기간 내내 트래픽이 있었다면 100 USD 플랜은 100 USD를 귀속시킨다 —
요청이 하나든, 백이든, 백만이든. 트래픽이 일찍 끊겼다면 그보다 적게 귀속시킬 뿐, 결코 더
많이 귀속시키지 않는다. **회계용으로만** 계산한다. 라우팅은 `marginal_usage`만 본다 —
이미 지불한 구독 비용이 포화된 플랜을 싸게 보이게 만들면 안 되기 때문이다. 두 값은 별도
필드이며 절대 섞지 않는다.

> ⚠️ **개정 2는 여기에 공식을 적었고, 그 공식의 합은 `plan_cost × H_N`이었다.**
> 규칙은 `기간비용 × (요청 marginal ÷ 기간누적 marginal)`이었고 요청마다 계산되어 원장에서
> 합산됐다. 동일한 요청 N개면 `plan_cost × (1 + ½ + ⅓ + … + 1/N)`이다: **100 USD 플랜이
> 요청 100개에서 약 519 USD를, 1,000개에서 약 749 USD를 귀속시켰고, 증가는 멈추지 않았다.**
> 조용히 교체하지 않고 기록으로 남긴다. 그 숫자는 이미 원장에 들어갔고, 거기서 파생된 모든
> 값 — 키별 귀속, 팀별 차지백, §8.5가 존재하는 이유인 notional 대 실제 비교 — 이 트래픽
> 양에 따라 달라지는 배수만큼 틀렸기 때문이다.
>
> 원인은 산술이 아니라 구조다. 각 몫은 *같은 양*에 대한 추정치였고 — 지금까지의 트래픽당
> 플랜 비용 — 하나의 양에 대한 추정치는 누적되는 것이 아니라 서로를 대체해야 한다. 더할 수
> 있는 것은 증분뿐이다.

그래서 기간의 귀속 총액은 **커지는 합이 아니라 갱신되는 하나의 누계**이며, 요청이 기록하는
몫은 그 누계를 현재 시점까지 끌어올리는 증분이다:

- **플랜은 자기 기간에 걸쳐 발생한다.** 정액 플랜이 사는 것은 *기간*이므로, 지나간 기간의
  비율이 곧 발생한 플랜 비용의 비율이다. 요청은 직전 정산 이후 발생한 몫을 기록한다. 기간에
  고르게 퍼진 요청들은 각각 `plan_cost ÷ N`을 가져간다 — 옛 공식이 첫 요청에게만 주던 값이다.
- **누적 사용량은 분모가 될 수 없다.** 기간의 총사용량은 기간이 닫히기 전에는 알 수 없고,
  기간 중의 모든 추정치는 실제보다 작다. 너무 작은 분모로 나눈 것이 모든 요청을 과다
  귀속시킨 원인이다. 미리 알 수 있는 분모는 기간뿐이고, 그래서 총액이 유계가 된다. 정확한
  사용량 가중 안분은 여전히 가능하지만 — 기간이 닫힌 *뒤* 원장의 marginal 컬럼에 대한
  롤업으로 — 실시간으로 정산되는 요청별 컬럼은 그것을 기다릴 수 없다. "누가 가치를
  소비했는가"는 §8.5의 notional이 키별·팀별로 이미 답한다.
- **정산된 행은 바뀌지 않는다.** 추정치를 고치자고 과거를 다시 쓰는 것은 고치려는 결함보다
  나쁘다. 운영자가 이미 보고 내보내고 청구한 숫자는 그대로 남는다. 몫이 증분인 이유가 바로
  어떤 행도 다시 쓰지 않기 위해서다.
- **상한은 구조적이다.** 경과 비율은 `Price`·`Settle`·`Explain`이 모두 통과하는 단 하나의
  함수 안에서 기간으로 클램프된다 — 아무도 지목하지 않았던 세 번째 호출 지점을 잡아낸
  `TotalNano` 하한과 같은 모양이다. 플랜을 두 번 귀속시킬 수 있는 호출 지점은 남아 있지 않다.
- **리로드는 청구 사건이 아니다.** 누계는 로드된 카탈로그와 수명을 같이하고 리로드는 새 카탈로그를
  만들므로, 열린 기간이 리로드 시점부터 귀속을 다시 시작해 남은 기간을 한 번 더 귀속시켰다.
  이것은 "리로드당 플랜 비용 하나로 유계"인 잔여 항목으로 기록되어 있었지만, 실측은 **리로드 20회에
  100 USD 플랜의 1,030 USD**였고, 기간의 90% 지점에서의 리로드 한 번이 **단일 요청에 91.00 USD**를
  얹었다 — 예산 홀드는 그것을 *그 요청의* 예산에 잡는다. 상한이 "의도된 변경 1회당"도 아니었다:
  `SIGHUP`은 무조건 재적용하므로, 타이머로 HUP을 보내는 설정 관리 에이전트는 타이머로 청구했다.

  이제 새 카탈로그가 **이전 카탈로그의 상태를 인계받는다** — 기간의 귀속 누계와 나노 미만 반올림
  이월. 중복 리로드를 억제하는 대신 여기서 닫은 이유는 중요하다: `SIGHUP`은 운영자가 외부 가격
  카탈로그 수정본, 모델 카탈로그 오버레이 수정본, 회전된 `key_file` 시크릿을 집어 올리는 유일한
  수단이고, 설정 파일의 mtime은 그 어느 것도 말해주지 않는다. *"파일이 안 바뀌었다"*는
  *"아무것도 안 바뀌었다"*가 아니므로, 리로드는 무조건인 채로 두고 대신 공짜로 만든다.
- **미래로 찍힌 정산은 현재로 클램프한다.** 누계는 앞으로만 움직이므로, 현재보다 앞선 시각으로 찍힌
  행은 그 시점까지 발생할 플랜 비용을 전부 귀속시키고 실제 기간의 나머지에는 아무것도 남기지
  않는다. 그 시각이 *다음* 기간에 떨어지면 기간 표식까지 앞으로 옮겨져, 실제 기간의 이후 행들은
  아래의 지각 행 분기를 타고 다음 기간은 이미 깎인 채로 열린다. 실측: 그런 행 하나가
  **100.00 USD짜리 7월에 10.00 USD만 귀속**시켰다. 지각 행 가드의 거울상이며, 악의 없이도 도달한다 —
  클러스터의 한 노드 시계가 앞서 가면 충분하다. 거부가 아니라 클램프인 이유는, 거부는 가격 산정
  호출 전체를 실패시켜 그 요청의 실제 marginal 비용까지 함께 잃기 때문이다. 시계가 왜곡할 수 있는
  것은 플랜 몫뿐이므로 조정되는 것도 그것뿐이다. 클램프는 정산에만 적용된다. `Price`와 `Explain`은
  아무것도 변경하지 않으며, 미래 시각의 가격 산정은 미리보기의 존재 이유다.
- **몫은 음수가 되지 않는다.** 열린 기간 안에서 순서가 뒤바뀌어 도착한 행은 이미 정산된 행이
  가져간 것을 회수하는 대신 0을 귀속시킨다.
- **요청이 없는 기간은 아무것도 귀속시키지 않는다.** 트래픽이 도중에 끊긴 기간은 끊기기
  전까지 발생한 만큼만 귀속시킨다. 플랜 비용은 여전히 발생했고, 그것의
  정직한 자리는 플랜 비용과 기간이 귀속시킨 총액의 *차이*다 — 조용한 한 달은 귀속되지 않은
  플랜으로 읽히고, 그것이 플랜을 갱신할 가치가 없다고 말해주는 숫자다. 없는 요청에, 또는 다음
  기간의 첫 요청에 귀속시키는 것은 둘 다 일어나지 않은 트래픽을 지어내는 일이다.
- **닫힌 기간에서 늦게 도착한 행은 플랜 비용을 0으로 귀속시킨다**(marginal 비용은 평소대로
  계산된다). 그 기간의 플랜 비용은 열려 있는 동안 정산된 행들에 이미 안분됐고, 추가 몫을
  제한할 누계는 사라졌다. 양의 몫은 무엇으로도 유계가 아니며 닫힌 기간을 플랜 비용 위로 밀어
  올릴 수 있다. 백필 가드와 같은 논리다: 늦은 행이 과다 귀속을 되살려서는 안 된다.

테스트가 강제하는 것은 공식이 아니라 이 성질이다: N이 1부터 10,000까지, 한 기간의 정산된
몫의 합은 정확히 플랜 비용이며, N = 100과 N = 1,000은 조화급수적 증가가 다시 돌아오지
못하도록 이름 붙은 행으로 남겼다.

### 8.2 매칭 — 사전 인덱싱 **[R1-10]**

구체성 순서: credential → deployment → (provider, model) → model → model prefix →
provider → default. 동률은 명시 priority, 그다음 규칙 id로 결정론적으로 깬다.

규칙은 **설정 로드 시 정적 차원으로 인덱싱**되므로, 요청은 자기 프로바이더/모델/크리덴셜에
해당하는 소수의 후보 규칙만 평가하고 시간 종속 술어만 요청 시점에 평가한다. 비용 기반
라우팅이 모든 후보를 평가하므로 요청 내 후보별 결과를 메모이즈한다.

### 8.3 산술 **[R1-11]**

정수 나노 단위만으로는 정밀도도 안전성도 얻지 못한다. 나노 미만 토큰 단가는 요청마다 0 또는
1로 반올림되어 체계적 오차가 쌓이고, 평생 누적은 부호 있는 64비트 나노를 넘길 수 있다.

- 단가는 **정확한 십진수**로 파싱한다. 이진 부동소수를 거치지 않는다.
- 곱셈은 **128비트 중간 정밀도**.
- 반올림은 **마지막에 한 번**, half-to-even, 나머지는 다음 정산으로 이월한다.
- 모든 쓰기는 범위 검사한다. 오버플로는 음수 비용이 아니라 오류다.

컴포넌트: input, output, cached read, cache write, reasoning, request, characters, **compute seconds, audio seconds**.

마지막 두 개는 원래 `seconds` 하나였고 요청의 벽시계 시간으로 가격이 매겨졌다. 그것은 GPU-초 요율에는 맞는 입력이지만 녹음 길이로 청구하는 전사(transcription) 벤더에는 틀린 입력이다 — 그래서 둘은 서로 다른 단위(`per_compute_second`, `per_audio_second`)의 별도 컴포넌트이고, 모호한 표기는 로드 오류이며, 한 축으로 인용된 규칙이 다른 축만 실은 요청을 만나면 가장 가까운 숫자에 요율을 적용하는 대신 **가격 미책정(UNPRICED)** 요청이 된다. 표와 측정치는 §10.7에 있다.

**사용량 카운트는 포함(inclusive)이고 요율표는 배타(exclusive)이며, 둘을 맞추는 일이 필요하다.**
§10.7은 `InputTokens`를 캐시 읽기·쓰기 접두부를 포함한 프롬프트 전체로, `OutputTokens`를 추론
토큰을 포함한 응답 전체로 정규화한다. 어떤 벤더의 요율표도 그렇게 표기되지 않는다: `input`은
캐시에서 제공되지 *않은* 프롬프트 토큰의 단가이고, 추론은 벤더가 따로 값을 매기지 않는 한
`output`에 접혀 있다. 그래서 **부분에 대해 선언된 요율은 그 부분을 부모의 수량에서 잘라낸다** —
`input`은 `input − cache_read − cache_write`에, `output`은 `output − reasoning`에 부과되고,
각 뺄셈은 그 규칙이 해당 하위 요율을 선언한 경우에만 적용된다 — 그리하여 모든 토큰은 정확히 한 번
부과된다. 선언되지 않은 하위 요율은 자기 토큰을 부모에게 남기며, 그것이 캐시 할인이 없는 벤더가
청구하는 방식이다. CONFIG §13.1a가 카탈로그 작성자가 읽는 자리에서 이 규칙을 말한다.

> ⚠️ **산술은 §10.7 자신의 경고 아래에서 그 반대를 했다.** `input`이 포함 프롬프트 전체에 부과되고
> `cache_read`가 그중 캐시된 부분에 *또* 부과되었다. §8.5의 예시 요율표에서 40토큰 캐시 접두부를
> 가진 120토큰 프롬프트와 15토큰 응답은 벤더의 **$0.0001266 대비 $0.0001606 — 27% 초과**로
> 청구되었고, 90% 캐시된 에이전트 턴에서는 **5.7배**였다. §10.7은 "잘못 매핑된 캐시 필드는 보이는
> 오류가 아니라 잘못된 청구서를 만든다"고 적고 있었고, 청구서가 틀린 동안 그 경고는 페이지에
> 있었다.
>
> 두 번의 깨끗한 패리티 실행과 한 번의 깨끗한 컷오버를 통과한 이유는 **어느 하니스도 가격을
> 선언하지 않았기** 때문이다 — 매 실행이 0과 0을 비교했다. 가격을 끈 채 회계 경로를 돌리는 검증
> 설정은 가격 결함을 볼 수 없으며, 이제 하니스 설정은 가격을 매긴다. 회귀 테스트는 pricing 패키지의
> 다른 함수가 아니라 손으로 계산한 벤더 금액에 대해 부과 금액을 검사한다: 그 함수들은 처음부터 서로
> 일치하고 있었다.

가격 미등록 모델은 비용 0 **이면서** 카운터를 올리고 경고를 남긴다. 조용한 0원 회계가
이 절 전체가 막으려는 실패 양식이다.

## 9. 저장소

원칙: **핫패스는 저장소를 만지지 않는다.** 원장과 롤업은 분리하고 보존기간을 달리한다.
**인덱스는 질의 집합에서 도출**한다. 마이그레이션은 임베드되어 기동 시 적용되며,
SQLite와 PostgreSQL이 하나의 스키마 정의를 공유한다.

주요 변경:

- **메시지 발췌는 원장에 인라인으로 두지 않는다 [R1-3].** 규모 상단에서 발췌 컬럼이 저장을
  지배하고 원장 쓰기를 함께 끌어내린다. 발췌는 `request_traces`에 샘플링·바이트 예산과 함께
  저장한다.
- **`responses_store`는 선택이 아니다 [R1-C7].** Responses API는 서버 측 대화 상태를 갖는다.
  개정 1은 그 상태를 둘 곳 없이 엄격 호환을 약속했고, 런타임 선택지(거부 또는 무시) 둘 다
  약속을 어긴다. `reasoning_blobs`가 §10.2의 무결성 보유 리즈닝 핸들을 응답 id로 보관해
  바이트 동일 재생을 가능하게 한다.
- **질의 집합이 인덱스를 결정한다 [R1-12].** 키별·팀별·trace id별·크리덴셜별 조회에 각각
  인덱스를 두고, 태그는 배열 스캔이 아니라 정규화 테이블로. 모든 원장 질의는 시간 범위와
  페이지네이션을 요구한다.
- **롤업은 목적별로 쪼갠다 [R1-13].** 전차원 큐브 하나는 영구히 비대해지고 한 키가 버킷을
  지배할 때 hot-row 경합을 만든다. 노드가 메모리에서 사전 집계 후 flush마다 한 번 병합하므로,
  한 행을 건드리는 쓰기 수가 요청 수가 아니라 노드 수로 묶인다.
- **파티션 관리는 writer와 같은 마일스톤 [R1-15].** 개정 1은 여섯 마일스톤 뒤로 미뤘고,
  그랬다면 계측 출시 후 첫 자정에 모든 INSERT가 실패했을 것이다.

예상 볼륨(추정이 아니라 명시):

| 티어 | 요청률 | 원장 행/일 | 원장 바이트/일 | 발췌(100%) |
|---|---|---|---|---|
| 노트북 | ~1 req/s | ~86 k | ~25 MB | ~44 MB |
| 팀 | ~50 req/s | ~4.3 M | ~1.3 GB | ~2.2 GB |
| 엔터프라이즈 | ~2 k req/s | ~173 M | ~52 GB | ~88 GB |

## 10. 프로토콜

### 10.1 중립 표현

프론트엔드가 `CanonicalRequest`로 디코드하고 백엔드가 인코드한다. N×M이 N+M이 되며,
이것이 "full protocol"을 상수 핫패스 비용으로 감당 가능하게 만든다.

#### 두 종류의 손실 **[R1-C6]**

개정 1은 손실을 "응답 헤더에 열거"한다고 했다. 헤더는 파라미터 이름의 평면 목록을 담으며,
한 종류에는 충분하고 다른 종류에는 무용하다.

**드롭 가능 파라미터** — 백엔드에 없는 노브. 요청의 의미는 유지된다.
`x-dorang-dropped-params`에 열거. 개정 1의 동작이 여기서는 옳다.

**구조적 다운그레이드** — 아예 표현할 수 없는 것:

| 교차 | 잃는 것 |
|---|---|
| 프롬프트 캐시 브레이크포인트 → 없는 프로토콜 | 캐싱 토폴로지, 따라서 비용 — 조용히 |
| 다중 블록 tool result → 단일 문자열 tool 메시지 | 텍스트 아닌 블록 |
| 문서/PDF 블록 → 없는 프로토콜 | 문서 전체 |
| 풍부한 stop reason → 작은 열거 | 어떤 종료 조건이었는지 |
| 블록별 속성을 가진 구조적 system → 단일 system 메시지 | 블록별 속성 |

> ⚠️ **"타깃이 표현할 수 있는가"는 잘못된 축이었고, 파라미터 넷이 틀린 쪽에 분류돼 있었다.**
> 모양(shape)에 관한 진술로 읽힌 그 기준은 `stop`·`n`·`logprobs`·`service_tier`를 드롭 가능
> 노브로 분류했다. 그 결과 stop 시퀀스가 드롭되면 호출자가 지정한 종료 지점을 넘어 생성이
> 계속되고 그 추가 토큰이 청구됐다. `n: 4`는 선택지 하나로 돌아와 `choices[3]`이 게이트웨이의
> 에러가 아니라 클라이언트 안의 인덱스 에러가 됐다. `logprobs: true`는 요청한 멤버가 없는
> 본문을 받았다. `service_tier: flex`는 호출자가 고르지 않은 가격대에서 실행되고 청구됐다.
> 넷 모두 `x-dorang-dropped-params`에 파라미터 이름을 실은 `200`으로 응답했는데, 이것은
> 동의가 아니다 — 아무도 파싱하지 않는 헤더가 "답이 요청한 그것이 아니다"라는 소식을 나르는
> 것일 뿐이다.
>
> 위 표 자체도 모양에 관한 것이 아니었다. **프롬프트 캐시 브레이크포인트가 여기 있는 이유는
> 잃으면 청구서가 바뀌기 때문**이고, 풍부한 stop reason은 어떤 조건이었는지를 잃기 때문이다.
> 그래서 축을 처음부터 실제로 결정하고 있던 질문으로 다시 쓴다:
>
> **없어지면 호출자가 받는 것 또는 청구되는 것이 바뀌는가, 아니면 dorang이 적용한 노브만
> 바뀌는가?** 노브는 드롭 가능하다. 그 밖의 것은 호출자의 동의가 필요하다.
>
> 이것이 모든 파라미터를 구조적으로 만들지는 않으며, 그 절제가 핵심이다. 샘플링 사전분포 —
> `logit_bias`·`top_k`·`frequency_penalty` — 는 사후조건을 진술하지 않는다. 어떤 벤더도
> 분포를 약속하지 않고, 같은 요청이 매번 다른 텍스트를 돌려주며, 사전분포가 드롭된 답은 그것을
> 실은 요청을 다시 뽑은 결과와 구분되지 않는다. "요청한 분포가 아니다"로 거부하면 OpenAI
> 계열로 가는 모든 교차에서 `top_k`를 거부해야 하는데 그것은 매일 일어나는 무해한 변환이고,
> 모든 요청에 `x-dorang-allow-lossy`를 붙이도록 학습된 호출자에게 그 장치는 아무것도 보고하지
> 않는다. **거부가 늘어나는 비용**은 "기본값을 하라"는 뜻의 값에서 상쇄된다: `n: 1`과
> `service_tier: auto`는 어떤 능력도 요구하지 않는다. 드롭해도 바뀌는 것이 없기 때문이다.
>
> 따라서 거부 집합은 두 반쪽으로 나뉘며, 둘의 차이는 거부 여부가 아니라 **보고 방식**이다.
> **위치가 있는(located)** 반쪽은 위 표이고 가리킬 인덱스를 갖는다
> (`messages[2].content[1]: application/pdf`). **물질적(material)** 반쪽은 `stop`·`n`·
> `logprobs`·`service_tier`이고, 호출자가 쓴 값과 함께 파라미터 이름으로 보고된다
> (`service_tier: flex`) — 이것이 `400` 본문의 `param`을 채울 수 있게 하는 것이기도 하다.
> 표는 COMPATIBILITY §7.9, 마스크는 `canonical.Material`.

PDF를 조용히 버리거나 캐싱 전략을 파괴하거나 stop 시퀀스를 무시하고 `200`을 돌려주는 것은
**에러보다 나쁘다** — 호출자가 알 방법이 없다. 개정 2는:

- 요청이 실제로 그런 구조를 담고 있고 선택된 백엔드가 표현할 수 없으면 **`400`으로
  즉시 실패**하며 기계가 읽을 수 있는 본문에 해당 구조를 명시한다.
- `x-dorang-allow-lossy: <구조>[,…]` 로 손실 변환에 명시적으로 opt-in할 수 있고, 이때
  적용된 손실은 `x-dorang-downgraded`로 보고된다.
- 라우팅 시 **표현 가능한 백엔드를 선호**한다 — 능력이 라우팅 필터가 되므로, 한쪽 프로토콜
  계열만 지원하는 구조를 쓴 요청은 그쪽으로 가고, 그런 배포가 없을 때만 실패한다.

첫째와 셋째는 별개의 의무이고 둘 다 구현돼 있다. 라우팅은 "이 모델의 어떤 배포가 표현할 수
있는가"에 답하고, 백엔드는 "선택된 그 배포가 표현할 수 있는가"에 — 그 배포가 선언한 능력
집합에 대해, §4.4의 엔진 정규화가 끝난 뒤에 — 답한다. 실제로 인코드될 요청이 존재하는 시점이
거기뿐이기 때문이다. 라우팅에서만 막는 게이트웨이는 두 능력 집합이 일치하는 동안에만 옳고,
어긋나는 날 조용히 다운그레이드한다. 전체 구조 목록은 호환성 문서의 버전 관리 표(§7.9).

### 10.2 리즈닝 레벨 맵핑

```
reasoning = { enabled, effort: none|minimal|low|medium|high|xhigh|max,
              budget_tokens?, summary }
```

#### 능력은 kind가 아니라 모델로 키잉한다 **[R1-C5]**

개정 1은 프로바이더 kind로 키잉했다. 두 번 틀렸다: 한 프로바이더 안에서도 모델 세대에 따라
리즈닝 제어가 바뀌고, 개정 1은 **특정 모델 버전 하나에서 관찰된** 2단계 effort 스케일을
패밀리 전체로 일반화했다. 그 패밀리의 다른 구성원에서는 리즈닝 제어가 조용히 무시되거나
거부된다.

개정 2는 **(kind, 모델 능력)** 으로 키잉하며, 능력은 버전 인지 규칙으로 매칭되는 모델
카탈로그에서 온다. 검증되지 않은 능력은 **가정하지 않는다** — 카탈로그가 `unknown`으로
표시하고, dorang은 제어를 생략한 뒤 `x-dorang-dropped-params`로 보고한다. 각 능력은
실제 엔드포인트로 검증한 날짜와 함께 카탈로그에 기록된다.

#### budget은 상수가 아니라 요청의 함수다 **[R1-C4]**

고정 effort→budget 표는 호출자가 작은 출력을 요청하면 깨진다. budget은 출력 상한보다 엄격히
작아야 하므로 모든 effort가 같은 값으로 붕괴해 스케일이 무의미해지거나, 표에 맞추려고 출력
상한을 올리면 **호출자의 요청 한도와 청구액을 조용히 배로 늘린** 셈이 된다.

```
budget = min( 표[effort], max_tokens − reserve )     reserve ≥ 1
budget < 최소_유효_budget 이면 이 요청의 리즈닝은 비활성화되고 그 사실이 보고된다
```

dorang은 리즈닝 budget을 맞추려고 **호출자의 `max_tokens`를 절대 올리지 않는다.**

#### 역방향 맵핑은 best-effort이며 그렇게 말한다 **[R1-C2]**

개정 1은 리즈닝 출력을 호출자 프로토콜로 "재조립"한다고 했다. 그 단어는 달성 불가능한 것을
약속한다. 어떤 프로토콜은 **무결성이 보호된 리즈닝 블록**을 붙이고 tool-use 교환의 다음 턴에
그것을 그대로 되돌려야 하는데, 게이트웨이는 다른 백엔드의 평문 리즈닝 필드에서 유효한
블록을 합성할 수 없다. 그리고 그 실패는 에이전틱 플로우의 **두 번째** 턴에서 터진다 —
발견하기 가장 나쁜 지점이자, 설계가 표적으로 명시한 플로우다.

- 리즈닝 **내용**은 best-effort로 정규화하고, 프로토콜 네이티브 블록에서 온 것이 아니면
  `x-dorang-reasoning: derived`로 표시한다.
- 무결성 자료를 지닌 리즈닝 **블록은 응답 id로 키잉된 불투명 핸들로 저장**되어, 호출자가
  되돌려줄 때 바이트 동일하게 재생된다. dorang은 그것을 위조하거나 재서명하지 않는다.
- 호출자가 선택된 백엔드에서 만들 수 없는 블록을 되돌리면 능력 라우팅이 가능한 백엔드를
  선호한다. 없으면 사유를 명시한 `400`으로 실패한다. 위조 블록을 전달하지도, 조용히
  버리지도 않는다.
- 리즈닝 표현 간 왕복은 **손실이 있고 비가역**임을 문서화하며, 2턴 tool-use 케이스에 대한
  적합성 테스트를 둔다.

### 10.3 파라미터

`drop_unsupported`(기본 on), `params.drop[]`, `params.set{}`, `params.default{}`.
모든 제거는 보고된다.

### 10.4 확장 헤더

식별·비용 헤더만 항상 붙는다. 나머지는 `x-dorang-detail: full` 요청 시 또는 설정으로 켠다.
개정 1은 모든 응답에 서른 개 남짓을 붙였는데, 중개자 헤더 크기 한계 위험이 있고 첫 스트리밍
바이트 앞에 바이트를 더한다 — 자기가 지키려던 목표에 반한다 **[R1-C9]**.

**어떤 비용 헤더도 스트리밍 요청의 비용을 실어 나를 수 없고, 그런 척하지도 않는다.** 헤더는 첫
프레임보다 먼저 쓰이고 요청은 마지막 프레임 뒤에 정산되므로, 스트림에서 `x-dorang-cost-usd`는
부재한다 — 가격 규칙이 없는 요청에서와 마찬가지로. dorang 자신의 어휘는 "가격 규칙 없음"과
"공짜"를 구분하기 때문이다. 레거시 미러 `x-litellm-response-cost`는 가격 미등록이 헤더 부재가
아니라 `0`으로 읽히도록 평소에는 무조건 나가지만, **이 한 경우에만 생략된다** — 아무도 측정하지
않은 0을 발행하는 대신에. 판별표는 COMPATIBILITY §7.7a에 네 상태로 있다. 스트리밍 비용은 숫자가
실제로 존재하는 아래의 종료 프레임과 원장으로 전달된다.

**스트리밍 전달 채널은 하나이고 opt-in이다 [R1-C9].** 개정 1은 종료 SSE 이벤트 *와* HTTP
트레일러를 약속했다. 트레일러는 죽은 채널이다 — 주요 LLM 클라이언트 라이브러리는 SSE 본문을
읽고 트레일러를 노출하지 않는다. 게다가 dorang이 만든 SSE 프레임을 주입하는 것은 업스트림
바이트를 손대지 않고 전달한다는 것과 모순된다.

개정 2: 스트리밍 응답의 사후 값은 클라이언트가 `x-dorang-usage-events: 1`로 opt-in할 때만
전달한다. 그렇지 않으면 스트림은 업스트림에 충실하게 유지되고(§7.2의 alias 재작성 제외),
값은 항상 존재하는 `x-dorang-request-id`로 원장에서 조회할 수 있다.

### 10.6 범용 패스스루 엔진

프로바이더 고유 경로는 매번 어댑터를 쓰는 게 아니라 **설정으로 열린다**. 인증 후 prefix를
떼어 base URL에 접합하고, 본문을 **파싱하지 않고** 양방향 스트리밍 릴레이한다. 계측은
best-effort이며 실패해도 요청을 실패시키지 않는다. WebSocket 업그레이드도 같은 엔진이 처리한다.

**보안 경계**: 매핑되지 않은 prefix는 열지 않는다(오픈 프록시 방지). 경로는 정규화하고
이탈을 거부한다. 프로바이더 크리덴셜은 클라이언트에 도달하지 않는다.

## 11. Batch · 유저 · 관리

### 11.1 Batch — 백엔드 독립

배치 스케줄러는 dorang 자체 것이다. 어떤 업스트림이 배치 엔드포인트를 노출한다고 가정할 수
없으므로 그것에 의존하지 않는다. 네이티브 배치 경로는 프로바이더별로 켜는 **선택적 가속기**다.

**대화형 작업은 모든 축에서 보호된다 [R1-12].** 개정 1은 배치를 *크리덴셜* 동시성의 몫으로
제한했는데, 그것은 *모델* 축을 보호하지 못한다 — 배치가 크리덴셜 몫 안에 있으면서도 한 모델의
한도 전체를 차지해 그 모델의 대화형 트래픽을 완전히 굶길 수 있다.

개정 2는 `capacity.interactive_reserve`를 쓴다: **모든** 축에서 상한의 일정 비율이 비배치
작업용으로 예약되며 배치는 그것을 점유할 수 없다. 시나리오 테스트에 모델 축 경합이 명시적으로
포함된다 — 개정 1의 테스트로는 잡히지 않았을 결함이다.

### 11.2 인증 / 11.3 UI / 11.4 유저·팀 / 11.5 이메일·Lua

Bearer → 스킴 무관 조회(§2.4) → 메모리 principal. 팀·유저·키 한도가 모두 적용되며 가장
엄격한 것이 이긴다. UI는 바이너리에 임베드된 SPA로 v1은 **키 / 모델·배포 / 사용량·비용**
세 화면. Lua 훅(`on_request`, `on_route`, `on_response`, `on_email`)은 명령어·메모리·시간
상한이 있는 샌드박스에서 돌며 핫패스 기본 비활성이다. 상한 초과 시 훅을 건너뛰고 경고
(fail-open), 단 `on_request`의 명시적 거부는 존중(fail-closed).

## 12. 관측

### 12.1 두 개의 계측 큐 **[R1-1, R1-2]**

개정 1은 링버퍼 하나로 가득 차면 원장을 버리면서 롤업은 정확하다고 주장했다. 양쪽 다 틀렸다.
원장을 버리는 것은 요구사항이 요청한 트레이싱을 정확히 잃는 것이고, 다차원 롤업을 정확히
유지하려면 키가 있는 집계를 건드려야 하는데 그것은 가정했던 공짜 스택 할당 연산이 아니다.

```
요청 완료
   ├─▶ 숫자 이벤트 → CPU별 고정 카디널리티 누산기 (항상 유지)
   └─▶ 트레이스 페이로드 → 제한 큐 → 로컬 영속 스풀 → 원장 (샘플링, 드롭 시 가시화)
```

- **숫자 회계는 절대 잃지 않는다.** 비용·토큰·오류 수는 어떤 백프레셔에서도 살아남는다.
- **트레이스 페이로드는 저장소 전에 로컬 디스크로 스풀**되므로, 저장소 정체가 데이터가 아니라
  디스크를 소모한다. 스풀까지 차면 드롭을 세고 `metering_degraded`를 헬스와 메트릭으로 알린다.
  조용한 손실은 없다.

### 12.2~12.4 트레이싱 · 메트릭 · 백엔드 메트릭

요청당 trace id와 지연 분해(큐, 라우팅, 용량 대기, 업스트림 연결, TTFT, 총). 메시지 내용은
기본 512자 발췌를 `request_traces`에 샘플링·바이트 예산과 함께. 백엔드가 메트릭 엔드포인트를
선언하면 큐 깊이와 캐시 사용률이 `least_busy`/`highest_tps`의 라우팅 신호가 된다(플래그로 opt-in).

## 15. 성능

### 15.1 프로파일별 목표 **[R1-8]**

지연 숫자 하나는 반증 불가능하다 — 목표를 못 지키는 경로를 범위 밖으로 정의하면 되기
때문이다. 목표는 프로파일별로 명시하고 측정 경계를 고정한다.

> **게이트웨이 오버헤드** = 요청 라인+헤더의 마지막 바이트를 읽은 시점부터 업스트림으로 첫
> 바이트를 쓴 시점까지, **더하기** 업스트림 마지막 바이트부터 클라이언트로 마지막 바이트를
> 쓴 시점까지. 업스트림 시간은 **제외**. 인증·라우팅·용량 획득·가격·파라미터 변환·계측
> 인큐는 **포함**.

| 프로파일 | p50 | p99 |
|---|---|---|
| `warm-local` (인증 캐시 히트, 로컬 용량, prefix on, ≤4 KiB) | **480 µs** (측정값. 200 µs로 공표했으나 측정된 적이 없었다) | 2 ms |
| `cold-auth` (인증 미스, 저장소 1회) | — | 15 ms |
| `shared-redis` (클러스터 정확 용량) | — | 5 ms |
| `external-auth` | — | 피호출자에 종속 (약속하지 않고 명시) |
| `lua-enabled` | — | + 훅 상한 |
| `prefix-1MiB` / `prefix-16MiB` | — | **55 ms / 852 ms** (측정값. 6 ms / 60 ms로 공표) |

기타: 스트리밍 추가 TTFT p99 < 1 ms(**측정 648 µs**) · 유휴 RSS(노트북) < 100 MB(**측정 62 MB**) ·
동시 1000 스트림 < 300 MB(**측정 256 MB**, **§15.4 replay 예산 포함**) · 계측 on/off < 5% (정상 상태
**및** 버퍼 만재).

**200 µs p50은 측정된 적이 없었고, 성립하지 않는다.** `testing/perf`가 조립된 게이트웨이를 실제 소켓 위에서
고정 지연 페이크 백엔드에 대고 재는 하네스다. 게이트웨이 오버헤드는 핸들러 안의 시간에서 업스트림을
기다린 나노초를 전부 뺀 값이며, 그 뺄셈은 요청 단위라서 p99가 의미를 가진다. 16코어 Ryzen 7 8745HS,
warm, prefix on, 트레이스 계측 전량 샘플링, 가격 규칙 100개, 배포 2개, 클라이언트 4개 기준:

| 요청 본문 | p50 | p90 | p99 |
|---|---|---|---|
| 256 B | 191 µs | 276 µs | 367 µs |
| 1 KiB | 248 µs | 337 µs | 457 µs |
| **4 KiB** (프로파일이 명시한 상한) | **492 µs** | 656 µs | **855 µs** |
| 16 KiB (프로파일 밖) | 1.27 ms | 1.65 ms | 2.03 ms |

즉 200 µs는 수백 바이트 요청에서만 성립했고 프로파일이 명시한 4 KiB에서는 한 번도 참이 아니었다. p99
2 ms는 두 배 이상의 여유로 성립한다.

**대용량 본문 행은 자릿수가 틀렸고 이름도 틀렸다.** 1 MiB는 공표 6 ms에 측정 **55 ms**, 16 MiB는 공표
60 ms에 측정 **852 ms**다. 더 쓸모 있는 결함은 이름 쪽이다 — **prefix 체인은 이 수치의 약 1%다.**
`internal/prefix` 자체 벤치마크로 16 MiB 체인은 **7.1 ms, 728 B, 17 할당**이고 2.36 GB/s로 도는데,
이것이 §7.4b가 약속한 O(log n) 다이제스트 · 해시 1패스 그대로이며 공표 전에 실제로 측정된 몇 안 되는
숫자다. 나머지 99%는 코덱이다. 싼 쪽 이름을 붙인 프로파일은 정확히 엉뚱한 최적화를 부른다.

**비용의 소재.** 설정 가능한 기능은 전부 공짜다 — prefix affinity, 트레이스 계측, 100개 가격 카탈로그,
두 번째 배포를 각각 켜고 꺼도 p50은 노이즈를 벗어나지 않았다(전부 끄면 341 µs, 전부 켜면 344 µs).
비용은 교차 프로토콜 게이트웨이가 본문에 대해 수행하는 JSON 패스 4회이고, 요청 경로가 태우는 CPU의
약 85%다. `internal/wire/openai.DecodeRequest` 단독으로 **31 MB/s, KiB당 143 할당**인데, 각 wire
타입의 `UnmarshalJSON`이 자기 바이트를 두 번 파싱하기 때문이다 — 한 번은 구조체로, 한 번은 모델링되지
않은 멤버를 분리하려고 `map[string]json.RawMessage`로(`wirejson.SplitExtra`).

### 15.2 기법

불변 라우팅 스냅샷(읽기 경로 무락) · 핫패스 무할당(필요한 필드만 스캔, 전체 언마샬 없음) ·
**단일 패스·무디코드 스트리밍 릴레이 [R1-C1]** · 튜닝된 커넥션 풀 · 분리된 비동기 계측 ·
O(1) 인증 · 샘플링 구조화 로깅.

### 15.3 처리량은 워크로드로 명세한다 **[R1-9]**

"20k req/s"는 요청이 무엇인지 말하지 않으면 무의미하다. 벤치 워크로드를 고정한다:
1 KiB / 32 KiB / 400 KiB 본문, 편향 분포의 키, 가격 규칙 100개 로드, prefix on/off,
실제 저장소로 영속되는 계측, 10분 정상 상태. 두 수치를 따로 보고하며 둘 다 지켜야 한다 —
**서빙 처리량**과 **지속 가능한 저장 처리량**.

### 15.4 replay 메모리는 프로세스 전역 예산 **[R1-6]**

폴백은 재전송을 요구하고 재전송은 본문 보관을 요구한다. 요청당 상한만으로는 경계가 아니다 —
상한 바로 아래의 동시 요청 다수가 메모리 목표 전체를 넘긴다. **프로세스 전역 replay 예산**을
두고, 들어가지 못하는 요청은 그래도 보관하는 게 아니라 non-replayable로 표시하고 헤더로 알린다.

### 15.5 핫패스 금지

동기 저장소 접근(정확한 공유 용량 모드의 의도된 1 RTT 제외) · reflection · 정규식 ·
포맷 문자열 생성 · replay 예산을 넘는 본문 버퍼링.
