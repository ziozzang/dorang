# Ollama 두 계정의 요청을 끊김 없이 나누기

Ollama Pro는 계정 하나에서 동시에 진행할 수 있는 요청이 3개다. 모델이
달라도 같은 계정의 요청은 함께 센다. 계정 두 개를 쓰는 단일 게이트웨이는
최대 6개를 실행하고, 나머지는 짧게 기다린 뒤 빈 계정으로 보낸다.
스트리밍 응답도 끝날 때까지 자리를 차지한다.

## 기존 설정으로 되는 부분과 코드가 필요한 부분

`capacity.credential_groups.<계정>.max_concurrency: 3`과 각 자격증명의
`capacity_group`을 연결하면 기존 코드에서도 계정별 제한이 적용된다.
제공자의 `max_concurrency: 32`만으로는 계정별 제한이 되지 않는다.
`key_rotation`의 개별 키 제한은 같은 계정에 속한 여러 키를 합산하지 않는다.

기존 일반 요청 경로는 모든 후보가 차면 즉시 429를 반환했다. 이번 변경은
다른 후보를 먼저 모두 확인한 후 기존 대기열에 들어간다. 같은 제공자·모델의
계정들은 함께 기다리므로 어느 계정이 먼저 비어도 진행한다. 대기 시간과
대기 인원은 기존 `max_queue_wait`, `max_queue` 설정을 따른다. 서로 다른
제공자·모델이 모두 바쁘면 첫 번째 후보의 계정 집합에서 기다린다.
대화 상태 때문에 특정 계정이 필수인 요청은 기존처럼 그 계정만 기다린다.

## 설정 변경안 — 아직 운영에 적용하지 않음

다음은 기존 YAML에 합칠 항목이다. 기존 `capacity.global`, 다른 계정 설정,
자격증명의 비밀값 참조, 모델 목록은 유지한다. 두 번째 `credentials:`나
`capacity:` 블록을 덧붙이지 말고 기존 항목을 수정한다.

```yaml
capacity:
  credential_groups:
    ollama-account-1: {max_concurrency: 3, max_queue: 10}
    ollama-account-2: {max_concurrency: 3, max_queue: 10}
  principals:
    default: {max_concurrent: 16, max_queue: 10, max_queue_wait: 2s}

# 기존 credentials 항목에 capacity_group만 추가한다.
# id: ollama-1  -> capacity_group: ollama-account-1
# id: ollama-2  -> capacity_group: ollama-account-2
```

명시적으로 별도 principal 제한을 둔 이용자는 그 항목에도 짧은 대기 상한과
대기 인원 상한을 설정한다. `ollama-web-1`처럼 별도 경로의 키도 같은 유료
계정이면 동일한 `capacity_group`에 연결해야 한다. 키 이름만으로 같은 계정인지
단정하지 않는다. 이 변경은 키나 권한을 새로 만들지 않는다.

## 오류를 받는 쪽에서 구분할 것

- `rate_limit_exceeded`: 동시 요청 또는 일시 속도 제한. 상위 서버가 보낸
  `Retry-After` 또는 복구 시각을 사용한다. 둘 다 없으면 `Retry-After: 1`로
  1초 후 재시도를 안내한다. 일시 제한은 서비스 고장 횟수에 넣지 않으며,
  복구 시각이 없는 일시 제한을 반복해서 받아도 대기 시간을 수분으로 늘리지 않는다.
- `insufficient_quota`: 상위 서버가 사용량·잔액 소진을 명시한 경우.
  예를 들어 `session usage limit exceeded`를 포함한다. 한도 소진으로
  잘못 표시된 동시 요청 오류는 `rate_limit_exceeded`로 바로잡는다.
- `capacity_unavailable`: 로컬 대기 인원이나 시간 상한에 도달한 경우.
  상위 서버로 초과 요청을 보내지 않고 429와 `Retry-After: 1`을 반환한다.

첫 계정에서 응답 본문을 전달하기 전에 받은 429는 기존 fallback 경로로
다른 계정을 시도한다. 이미 스트림 본문을 전달한 뒤에는 중복 답변을
막기 위해 다른 계정으로 재실행하지 않는다.

## 운영 검토에서 반드시 구분할 범위

작업 기준은 운영 blue/green 이미지의 소스
`459c848af308ef769acd3d1fc41889afdce7c6f2`다. 이 변경은 배포하지 않았다.
기존 작업 폴더의 커밋되지 않은 변경도 수정하지 않았다.

현재 운영 설정은 `cluster.enabled: true`, `capacity_mode: shared-pg`다.
현재 동시성 처리는 살아 있는 노드 수로 한도를 정적으로 나누며, 놀고 있는
노드의 몫을 활성 노드에 빌려주지 않는다. 예를 들어 노드가 3개라면 계정별
3개 설정은 각 노드에서 계정별 1개만 허용한다. 따라서 아래 단일 프로세스
시험의 합계 6개를 현재 blue/green 구성의 처리량으로 해석하면 안 된다.
또한 노드가 계정 한도보다 많아지면 최소 1개 보장 때문에 전체 한도를
넘을 수 있는 기존 제약이 있다.

운영 전체에서 계정별 3개와 활성 노드의 합계 6개를 동시에 보장하려면,
대기 노드와 기존 :4000 소비자까지 포함해 슬롯 소유 방식을 별도로 정해야 한다.
이를 피하려고 계정 한도를 6이나 9로 올리거나 클러스터를 끄지 않는다.
게이트웨이를 통하지 않는 같은 계정의 사용량도 이 로컬 계수에는 포함되지 않는다.

추후 승인된 운영 반영은 기존 `dorang-rollout`의 blue/green 절차를 따른다.
격리된 커밋에서 이미지를 만들고, 대기 노드에서 준비 상태·실제 호출을 확인한
뒤 경로를 전환하고 이전 요청을 배출한다. 기존 :4000 인스턴스도 이 패치의
자동 적용 대상이 아니므로, 직접 연결 소비자를 확인해야 한다.

## 확인한 시험

`internal/app/ollama_capacity_test.go`는 가짜 상위 서버와 실제 HTTP 처리 경로로
다음을 확인한다. 외부 유료 모델은 호출하지 않는다.

- 두 모델에 걸쳐 동시 10개 요청: 계정별 최대 3개, 합계 6개 실행, 4개 대기.
  일반 응답과 스트리밍 응답을 각각 시험한다.
- 첫 계정을 계속 점유해도 대기 요청은 빈 두 번째 계정으로 진행한다.
- 첫 계정의 상위 429는 두 번째 계정으로 한 번씩 시도하여 성공한다.
- 두 계정 모두 일시 제한이면 429의 코드와 `Retry-After`가 올바르다.
- 대기 인원 초과는 바로 거절하고, 대기 만료와 요청 취소는 상위 요청이나
  대기 슬롯을 남기지 않는다.

`internal/backend/errors_test.go`는 일시 제한과 실제 한도 소진을 구분하고,
기존 복구 헤더 전달 시험은 상위 서버의 복구 시간이 우선함을 확인한다.
다중 운영 노드에서 합계 6개를 보장하는 시험은 수행하지 않았다.
